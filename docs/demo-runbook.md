# Person 3 deployment and demo runbook

## Artifact handoff (Person 1 → Person 3)

Use a **verified HTTPS service endpoint** for the first integration. Provide `repository`, `productName`, base URL, health path (default `/health`), POST run path (default `/run`), required environment variable **names**, input/output JSON schemas, known-good input, expected output structure, and verification evidence. The recovered service must perform the real work; this Worker only forwards calls. Set `RECOVERED_REPOSITORY`, `PRODUCT_NAME`, `CAPABILITY_BASE_URL`, `CAPABILITY_HEALTH_PATH`, and `CAPABILITY_RUN_PATH` as appropriate. The Worker POSTs the `input` field of `{ "input": ... }` to the recovered endpoint as JSON; the service's JSON response is returned in `{ "success": true, "result": ..., "metadata": ... }`. A Dockerfile/native artifact needs a separate Cloudflare Containers deployment and HTTPS service URL; it cannot be called by a Worker until deployed. Do not set the artifact to a mock service and label it recovered.

Person 2 can use `/product` (product UI), `/api/status` (deployment, artifact, Stripe test price, QA), `/api/checkout` (POST, returns URL), `/api/checkout/verify?session_id=...`, `/api/entitlement`, and `/api/product/run` (POST `{ "input": ... }`). The dashboard may show `pending` when a real handoff or QA result is absent. Cookie-based access is per browser; it is not account-based identity.

## Shared status contract

`GET /api/status` returns `selectedRepository`, `resurrection.status`, `artifact.status`, `deployment.status`/`productionUrl`, Stripe test price `status`/`priceId`/`amount`/`currency`, `qa.status`, and `latestError`. `pending` is an absent handoff/prerequisite; never change resurrection, artifact, or QA to `ready` without evidence. Current responses truthfully report no Person 1 handoff, a live Worker, ready test-mode billing, and QA pending. `/afterlife/` renders these same service fields.

## Reset and troubleshooting

Use a fresh private browser session for unpaid-path testing; deleting a browser cookie does **not** erase a real paid Stripe transaction. For a new paid run use a new Stripe test Checkout Session. Never reset a customer's entitlement by trusting browser flags. Inspect `/health`, `/api/status`, Wrangler logs, and Stripe test-mode webhook delivery logs. A pending QA state means independent QA has not been recorded, not that it passed. No autonomous Brainbase QA is attached until Person 1 exposes its real workflow. Back up the product URL and known-good input once actually verified; do not manufacture status or a backup recording.
