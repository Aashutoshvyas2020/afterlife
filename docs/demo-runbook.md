# Person 3 deployment and demo runbook

## Artifact handoff (Person 1 → Person 3)

Use a **verified HTTPS service endpoint** for the first integration. Provide `repository`, `productName`, base URL, health path (default `/health`), POST run path (default `/run`), required environment variable **names**, input/output JSON schemas, known-good input, expected output structure, and verification evidence. The recovered service must perform the real work; this Worker only forwards calls. Set `RECOVERED_REPOSITORY`, `PRODUCT_NAME`, `CAPABILITY_BASE_URL`, `CAPABILITY_HEALTH_PATH`, and `CAPABILITY_RUN_PATH` as appropriate. The Worker POSTs the `input` field of `{ "input": ... }` to the recovered endpoint as JSON; the service's JSON response is returned in `{ "success": true, "result": ..., "metadata": ... }`. A Dockerfile/native artifact needs a separate Cloudflare Containers deployment and HTTPS service URL; it cannot be called by a Worker until deployed. Do not set the artifact to a mock service and label it recovered.

Person 2 can use `/product` (product UI), `/api/status` (deployment, artifact, Stripe test price, QA), `/api/checkout` (POST, returns URL), `/api/checkout/verify?session_id=...`, `/api/entitlement`, and `/api/product/run` (POST `{ "input": ... }`). The dashboard may show `pending` when a real handoff or QA result is absent. Cookie-based access is per browser; it is not account-based identity.

## Initial setup

1. `npm install`; `npx wrangler --version`; `npx wrangler whoami`; `npx wrangler deploy --help`. If not authenticated, `npx wrangler login` for persistent production access. A temporary public proof succeeded using `npx wrangler deploy --config wrangler.dummy.jsonc --temporary` at `https://afterlife-dummy.blend-grouse.workers.dev/health`; this preview account expires and is **not** the production account. Once authenticated, run `npm run deploy:dummy` and verify its actual `/health` URL. Never infer public deployment from local Wrangler.
2. Create a Cloudflare D1 database with `npx wrangler d1 create afterlife-billing` (check CLI help), copy its real database ID to `wrangler.jsonc`; do not commit a fabricated ID. Configure the Worker secrets with `npx wrangler secret put STRIPE_SECRET_KEY` and `npx wrangler secret put STRIPE_WEBHOOK_SECRET`. Both must be **test-mode** values. Use `STRIPE_PRICE_ID` for an existing **active one-time test-mode** price (not created per request). Find/reuse the product and price in Stripe Dashboard test mode; note price ID and configured amount. Never commit keys, `.dev.vars`, or `.env`.
3. Set `PUBLIC_URL` to the actual Worker HTTPS URL. Configure Stripe test-mode endpoint `https://<worker>.workers.dev/api/stripe/webhook` and subscribe only to `checkout.session.completed`. Put its signing secret in the Cloudflare secret. `npm run deploy:prod` validates configuration, applies D1 migrations, deploys, and checks health. Confirm with `curl -fsS https://<worker>.workers.dev/api/status`; Stripe status must be `ready`, artifact status `ready` only after the real endpoint is healthy.
4. Local dev uses `.dev.vars` (gitignored) with the same key names and `npx wrangler dev`; local D1 migrations: `npx wrangler d1 migrations apply DB --local`. Run Stripe CLI (`stripe --version`, `stripe --help`, `stripe listen --help`, `stripe trigger --help` first) and forward webhooks to `http://localhost:8787/api/stripe/webhook`; use the signing secret from the active listener in `.dev.vars`. Test duplicate delivery; access must not change incorrectly.

## Live golden path / fallback

A: Supply known-good candidate URLs to Person 1's actual evaluation UI; require a recorded FUND decision and verified recovered service. B: Start from Person 1's already verified recovered HTTPS artifact (do **not** claim a fresh resurrection). C: Use the already deployed verified product (do **not** claim a new deployment). The candidate set and input must come from Person 1's verification: they are **not yet provided**. Record the exact repository, known-good JSON input, expected output type, and URL after handoff. Never show a cached result as a live execution.

From a real healthy production URL: open `/product`; inspect test-mode amount; buy; complete Stripe **test** Checkout with Stripe's documented test card; return to `/success?session_id=...`; verify status is paid; refresh the page; use the actual recovered capability. Before payment, manually POST `/api/product/run` and confirm HTTP 403. Cancel a separate Checkout and verify access remains unpaid in a fresh browser. Run `./scripts/smoke-test.sh https://<worker>.workers.dev`; it requires healthy artifact, live Worker, and verified Stripe test price, and rejects unauthorized runs. To additionally verify paid execution, supply `[known-good-input.json]` and `SMOKE_COOKIE_FILE` (a securely stored paid browser cookie jar); it checks a live result. Repeat the complete customer path before judging. The smoke script is not an automated card payment.

## Reset and troubleshooting

Use a fresh private browser session for unpaid-path testing; deleting a browser cookie does **not** erase a real paid Stripe transaction. For a new paid run use a new Stripe test Checkout Session. Never reset a customer's entitlement by trusting browser flags. Inspect `/health`, `/api/status`, Wrangler logs, and Stripe test-mode webhook delivery logs. A pending QA state means independent QA has not been recorded, not that it passed. No autonomous Brainbase QA is attached until Person 1 exposes its real workflow. Back up the product URL and known-good input once actually verified; do not manufacture status or a backup recording.
